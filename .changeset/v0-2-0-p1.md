McpGuard v0.2.0: the guard now works over HTTP, and the documentation says plainly what it
protects and what it does not. This note covers the HTTP gateway; the health profile, the tier-2
judge, `servers.<name>.roles` and the telemetry changes have notes of their own, and the
breaking changes in them stay in force.

`mcpguard serve` was a command that refused to run. It is now a guarded HTTP gateway: the three
gates `wrap` has (`tools/call`, `resources/read`, `tools/list`) run on the same code, one path per
server (`/mcp/<name>`), each with its own rules, its own `guardlock.json` entry and its own
connections. Servers come from `servers.<name>.upstream` in the policy (`{ url }` or
`{ command, args }`) or from the command line (`--upstream <url>` or `-- <command>`); naming the
same server in both is a start-up error. Tool names, URIs and capabilities pass through
untouched: there is no merging and no name prefix.

Both MCP protocol eras are served side by side, the legacy one with sessions and the modern one
without, and nothing is translated between them: a request whose era the upstream does not
speak is refused. A request is attributed to a session on the ADR-006 ladder (the trace id of
`_meta.traceparent`, then the `tunedness.session-id` baggage member, then `Mcp-Session-Id` on the
legacy era, then a best-effort guess from `clientInfo` and the remote address), and the record says
which rung answered and whether it was exact. McpGuard writes `tunedness.session-id` into the
`_meta` it forwards (an existing member is left alone), so an inner proxy such as AgentFuse adopts the same session.
`session.max_sessions`, `session.max_upstream_connections` and `session.idle_timeout` bound what a
caller can make it hold; a full connection table answers `503` with `Retry-After` and evicts no
one. The gateway never retries a `tools/call`.

The caller's identity ladder gains a `token` rung: `auth.tokens` holds the SHA-256 of each static
bearer token and the identity it stands for. With tokens defined, a request without a valid one
gets `401`, and the token is never written to a log. That identity is exact; `clientInfo` stays
the inexact fallback.

The defaults are conservative. It binds `127.0.0.1` (port 8766). Host and Origin are always
checked and no CORS header is written. A bind to anything but loopback does not start without
`auth.tokens` and `http.allowed_hosts` (exit code 3). A POST that is not JSON gets `415`, and
`http.max_body_bytes`, `http.max_upstream_response_bytes` and `http.max_inflight` bound the rest.
There is no TLS: the gateway says at start-up that it speaks plain HTTP, and it is meant to sit
on loopback or behind something that terminates TLS.

What it does not do, stated so nobody has to find out:

- A modern multi-round-trip (`input_required`) result does not pass through the shared upstream
  connection; the call fails. A test pins it.
- "Exact" identity is the caller's declaration, not proof. The threat model is an injected model,
  not a malicious client, which can split a sequence across trace ids to get around a
  combination rule.
- Legacy sessions live in the process's memory, so running several gateways needs sticky routing.
- mTLS and trusted-header identity are not implemented; neither are OAuth token exchange and
  the Tunedness Control Plane.

The manifest halt is now sticky, in `wrap` and in `serve`. A server whose tools stopped matching
its pin stays refused for every session, including ones opened later, until `lock --accept` or a
restart; a later list that happens to match the pin does not reopen the gate. Without this, a
server that alternates between two lists could reopen the gate for itself.

Not covered, and written down as the product's boundary: only `tools/call` results,
`resources/read` contents and `tools/list` are scanned. `prompts/get`, `sampling/createMessage`,
elicitation and every method outside the spec are forwarded untouched.

Measured, and not a promise: the scan's p95 stays under 20 ms up to 32 KB per result on every run
made for this release, and past that depends on the machine. The health recognisers meet their
gates on a synthetic corpus written by the same hands as the recognisers (in-sample); on a holdout
of 48 non-clinical collisions, all 48 were still masked. The judge's latency and catch rate are one
model on one machine. The figures and where they come from are in the README.

`mcpguard serve` and `servers.<name>.upstream`, `auth`, `http` and `session` are new in the policy
schema; `@tunedness/mcpguard-proxy` exports the gateway handler.
